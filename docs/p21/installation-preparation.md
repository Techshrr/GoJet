# Root-private installation preparation

The trusted root tool `installer/bin/prepare-installation.php DIRECTORY RELEASE
MANIFEST_SHA SOURCE_SHA` reads a bounded JSON document from stdin containing
`configuration` (the native configuration profile), `admin` (email, display_name,
password), and `tls` (certificate, private_key, http_port). It verifies the entire
release against the separately approved manifest digest and source before running
its native identity probe. It does not connect to MySQL or start services.

The root preparation entrypoint accepts omission of `configuration.secrets` and
then generates six independent 256-bit service keys plus a random key ID using
`random_bytes`. A supplied key set remains subject to the original strict compiler;
null, empty or partial sets do not silently select defaults. Generated values are
never returned on stdout and are stored only in the existing sealed private plan
(environment files and the administrator request). The pure configuration compiler
still requires explicit keys; this convenience exists only in root preparation.

Keys have no consumers before successful plan publication. Failed pre-publication
validation may discard unused in-memory keys. Once published, retries with omitted
or supplied keys reject the existing destination without changing any plan bytes;
execution and recovery read that plan and do not regenerate keys. Never remove a
published plan to retry or rotate keys. This does not yet expose a web configuration
route; the future web draft boundary must reject client-selected service keys.

The tool derives all eight environment files, the product Nginx configuration and
the existing root data request and dependency probe settings from this single profile. Database, Redis, origin,
Admin encryption key and release identity therefore cannot diverge through separate
operator inputs. Storage must not overlap the release or prepared job; TLS files
must be distinct and outside writable storage and the prepared job. These are path
conflict checks, not proof of storage availability or existing site compatibility.

Publication uses a parent lock, private staging, fsync and rename into a previously
absent directory. Directories are root0700 and files root0600. The seal binds the
exact generated bytes, external TLS hashes and permissions, approved manifest and
source. This is a root-controlled integrity record, not a signature against a
malicious root operator. Keep the approved source and manifest outside web control.
Never expose the prepared directory or stdin credentials to Installer FPM.

`installer/bin/run-prepared-data.php DIRECTORY` rechecks the private directory,
exact input inventory, links, ownership, modes, hashes, TLS and complete release
and runs the existing live dependency preflight before delegating to the existing
DataBootstrap worker. Schema3 plans bind the probe inputs and service units; older preparation
records are rejected and require a fresh destination. Readiness is never cached
from preparation. Stopped Nginx/FPM/Redis or changed storage permissions reject
before the data journal or any migration is created. Restoring dependencies permits
the unchanged plan to proceed. This does not eliminate failures occurring after
preflight: the data worker still records those failures and blocks unsafe retry. That worker retains its
exclusive lock, immutable migrations, inherited Admin bootstrap, durable journal,
repeat no-op and failure/interruption recovery barrier. Admin business validation
remains with the existing native authority. Failed data initialization requires
verified recovery; editing inputs is not a retry mechanism.

The payload CI exercises the actual archive against native MySQL8, Redis and
Nginx, checks refusal before any database mutation, applies all31 migrations,
creates exactly one initial administrator/audit event, and checks repeat no-op.
This is the root preparation/data phase only. Web submission, site conflict checks and dependency rechecks at service activation, service activation, final health and completion lock
are still required before an installable release or P21 closure.

## Prepared systemd units

Schema3 preparation also seals eight unit files derived from the verified packaged
units. Only the release WorkingDirectory/ExecStart, private EnvironmentFile and the
two file-consuming services' ReadWritePaths change. Fixed nonroot identities,
restart policy, dependencies and sandbox protections remain intact. Paths accept
only literal safe components, with no whitespace or systemd specifier expansion.
Schema1/2 plans require fresh preparation. No units are installed or enabled by
preparation or the data worker.

The native payload fixture now invokes the shipped root activation CLI in a
disposable host. It installs the exact generated units, starts all eight real binaries, and
checks their actual process UIDs, executable paths, running states and zero
restarts. It exercises API authentication and an absent-code redirect response,
and writes to the custom storage directory from the actual API/fileworker mount
namespaces as gojet. Units are stopped, disabled and removed in finally. Test
releases live outside /tmp because the production units retain PrivateTmp=yes.
These are service activation/startup proofs, not full business health,
external SMTP delivery, production deployment, final lock or whole P21 acceptance.

## Root service activation

`installer/bin/activate-services.php DIRECTORY` is a root-only CLI. The fixed
root authority directory `/var/lib/gojet-installer-authority` must first be
provisioned using the packaged tmpfiles policy. Its lock serializes activation
across all jobs; an installed.lock blocks this initial-install path. The executor
revalidates the full prepared plan and current dependencies, requires the exact
completed data journal, and refuses existing units, aliases, wanted symlinks or
drop-in overrides. It accepts no command, binary, unit-name or destination override.

It publishes the eight sealed units to /etc/systemd/system using exclusive create,
syncs them, enables them and starts the real logreceiver before its consumers.
Readiness checks actual nonroot executable identities, enabled/running states,
zero restarts, API discovery, redirect database/cache health and the private log
socket. Repeating a successful request rechecks current health and returns no-op.
The private services.json journal records publication, startup and readiness.

On failure, cleanup stops/disables only the units created by this invocation,
after verifying their bytes and ownership, then removes those units. It does not
stop an unrelated listener, modify existing units, undo migrations or remove data.
A changed unit or incomplete cleanup requires operator review. Failed or interrupted
activation cannot be retried directly. The root-only
`php8.3 installer/bin/recover-services.php DIRECTORY` command holds the same global
lock, rechecks the sealed release, live dependencies and completed data identity,
and inspects all eight unit paths, loaded fragments, overrides and enable links
before stopping anything. It refuses foreign or changed configuration, an existing
site journal, or the final completion marker. Exact owned units are stopped,
disabled and removed; data is preserved. Successful recovery durably records
`recovered`, its prior phase and a recovery counter, permitting fresh activation.
Repeated recovery is a no-op. If prerequisites are unavailable or bytes changed,
restore verified prerequisites or obtain operator review; do not delete journals.

Native CI exercises occupied-port failure and this shipped recovery command, then
SIGKILLs the actual root worker after observing the actual API startup failure.
It checks blocked retry, changed-unit refusal, explicit cleanup and successful
reactivation. This covers service-worker termination, not power-loss, site recovery
or full upgrade/restore.

Privileged activation is exercised only in isolated CI;
no production deployment is authorized by this implementation.

## Root site activation

`installer/bin/activate-site.php DIRECTORY` uses the same fixed root activation
lock and requires verified ready services, the complete prepared seal and current
dependencies. It publishes only `/etc/nginx/conf.d/gojet.conf`, with root0644,
exclusive creation and fsync. It refuses an existing target, an existing Nginx
listener on either intended port, unsupported include authority or Nginx warnings.
The Ubuntu conf.d wildcard must be active. Operators must resolve site conflicts
explicitly; this initial-install path never edits other vhosts or reuses ports.

The native parser checks the combined Nginx configuration before reload. A private
site.json records publishing/reloading/site-configured. Repeat verifies identity,
permissions and native syntax without reloading. A failed/interrupted journal
blocks automatic retry. On failure, only the exact owned file can be removed;
if reload was attempted, restoration is also reloaded. Failed restoration remains
explicitly incomplete. This does not roll back service or database state.

CI injects an actual failing systemd ExecReload on a disposable Nginx instance,
checks owned-file removal and failed-retry barriers, restores the command, and
performs explicit recovery through the shipped root CLI. Successful execution then serves the
actual packaged website bytes and real API/redirect services through verified
localhost TLS. HTTP canonical redirect, authorization401/403, wrong Host421 and
Installer404 are checked. Existing operator files and inline listener declarations
are preserved. The fixture removes only its own vhost and reload override.

site-configured records native syntax/reload completion, not end-to-end business
health. Final TLS/provider health, browser flow, completion lock, crash recovery
and G11 remain required. No production deployment or whole P21 closure is claimed.


## Explicit initial site recovery

Run `php8.3 installer/bin/recover-site.php DIRECTORY` as root after investigating
a failed/interrupted initial site apply. It shares the service activation lock,
requires the sealed release and ready services, refuses installed.lock or a
successful site, and only removes a root-owned exact sealed gojet.conf. Changed
bytes, symlinks and foreign authority require operator review. It validates and
reloads the remaining native Nginx configuration before recording `recovered`.
Failed restoration stays `recovering`; the same command may resume after fixing
the prerequisite. Data and service journals remain unchanged. Recovery retains
the prior phase and count, permitting subsequent site activation. Repeated recovery
revalidates and reloads the baseline without changing the recovered journal.

The native test uses the shipped recovery command after actual reload failure,
then kills the actual root worker during a delayed PID1 reload. The real Nginx
reload completes and serves the actual TLS site while the journal stays interrupted;
recovery removes the owned vhost and restores the baseline. It tests changed-site
preservation, global-lock/nonroot/completion-marker denial, closed recovered
listeners and successful reapplication. It does not prove machine power-loss or
full upgrade/restore. No final completion lock or production deployment is implied.

## Final native health and completion authority

After data, services and site apply, root may run
`php8.3 installer/bin/check-installation.php DIRECTORY` for a current health check.
`php8.3 installer/bin/complete-installation.php DIRECTORY` repeats those checks and
publishes `/var/lib/gojet-installer-authority/installed.lock` only on success.
Both use the same global activation lock and fixed command set. There is no HTTP
success flag or arbitrary root command interface.

Checks bind the approved package, sealed configuration/TLS files, completed data
and site journals, all current native dependencies, and all eight enabled nonroot
service executable identities and health. Local HTTPS uses the sealed certificate
bundle as trust, verifies the configured peer name/SNI, never resolves a remote
host or follows redirects, and limits each response to 1MiB and a 3-second stream
timeout. The three SPA entry bodies and a Docs index must match packaged bytes;
provider discovery must return JSON, private APIs must deny anonymous access,
Installer paths must be404, and a wrong Host must be421. Native readiness is
rechecked after HTTP probes.

The root0600 completion record contains only source, manifest and seal digests.
It is fsynced in a staging file and atomically linked into place without replacing
an existing file or symlink; the containing directory is fsynced before success.
A matching repeat acknowledges existing completion without rewriting it. It is
not a claim that services will remain healthy forever. An interrupted publication
or damaged authority remains closed to normal apply and requires operator review.
Existing Installer HTTP access returns404 after this marker is present.

Native CI exercises stopped worker/Nginx refusal, lock contention/nonroot/symlink
refusal, and a live unapproved TLS certificate while the disk config is restored
to approved bytes. None may write completion. It then checks health-only mode,
actual completion, exact repeat, all apply/recovery barriers and HTTP adapter404.
The marker is removed only during teardown of the disposable CI installation.
This proves the native CLI completion path; interactive web submission, full
upgrade/restore, browser verification and release/G11 closure remain required.
Package metadata remains `installable=false` until the complete P21 gate passes.

## Single-command native apply

After root prepares and reviews the sealed plan, run
`php8.3 installer/bin/apply-installation.php DIRECTORY`. The packaged entry point
executes data bootstrap, eight-service activation, site activation and final live
health/completion through the existing phase authorities. Only final completion
produces success output. It does not accept raw web input, arbitrary commands or
client-supplied phase results.

A fixed root0600 `installation-apply.lock` serializes complete apply invocations.
The data phase also holds the shared service activation lock; later phases acquire
that lock themselves. Every phase revalidates its prerequisites. Completed phases
retain their existing no-op semantics; failed/interrupted journals require the
explicit phase recovery command before another apply can proceed. The orchestrator
never deletes journals, rolls back data or silently resets a failed phase.
A matching final marker is acknowledged without rewriting it; a different sealed
plan cannot adopt it.

Native CI starts from a second empty MySQL database and verifies contention and
nonroot refusal before mutation. A real API-port conflict fails after data bootstrap
without final completion; direct retry stays blocked. Explicit service recovery
then permits the same apply command to finish. All31 migrations and the single
administrator/audit event remain intact, and the final marker/repeat are checked.
System changes and marker removal occur only in disposable CI. This CLI closes
native orchestration; interactive web-to-root submission remains separate work.

### Root-approved web apply mailbox

The shipped `provision-web-apply.php PREPARED_DIRECTORY NEW_STATE_DIRECTORY BOOTSTRAP_SHA256`
command verifies the sealed plan and provisions a dedicated `gojet-installer` state directory
starting at the services step. This is specifically an already root-approved plan; it does
not claim that the browser collected or validated environment/data/site/admin forms.
The dedicated system account must already exist. The new state directory must be outside
release, preparation and storage, beneath root-owned non-writable ancestors. Configure the
existing native installer FPM boundary with this directory and the same bootstrap digest.

After bootstrap authentication, `POST /install/services` accepts only JSON `{"csrf":"..."}`
with the existing session cookie and exact HTTPS Origin. It consumes the one-time CSRF,
persists checking, and exclusively publishes a small seal-digest request. HTTP 202 means
queued, not installed. No path, configuration, command, success flag or secret is accepted
by this endpoint. Normal unprepared wizard sessions cannot jump to this step.

The operator invokes `php8.3 installer/bin/run-web-apply.php` as root. This command takes no
arguments: it reads the fixed root-private `/var/lib/gojet-installer-authority/web-apply.json`,
checks the unprivileged mailbox ownership/mode/link count/bounded contents against that
binding, verifies the seal and package/dependencies again, and writes an exclusive durable
`web-apply-started.json` before calling the existing native installation orchestrator.
Only that orchestrator's successful live health checks can write the final `installed.lock`.
The HTTP adapter then returns 404. Neither the mailbox nor web state is completion authority.

There is deliberately no automatic retry or background worker installation in this increment.
Partial provisioning, partial mailbox publication, a failed worker or an interrupted worker
leaves a barrier for root inspection; re-authentication cannot reset it. Follow the existing
phase-specific recovery procedures and explicit root apply after diagnosis. Do not remove
root receipts to retry browser requests. Until final completion, the web state stays checking;
it does not yet project phase failures or provide an interactive progress experience.
Bootstrap-to-product vhost transition and the complete interactive/browser flow remain open.

The native payload fixture exercises the shipped HTTP adapter as the real unprivileged
installer account, rejects missing auth, invalid CSRF, extra fields, replay, forged digests,
unsafe modes, symlinks and an existing started receipt, then executes the real root worker
against the prepared native database and eight services through HTTPS health and final lock.
This is HTTP-adapter integration with injected trusted server variables, **not** a claim of
real browser/TLS submission. The separate native web fixture remains the TLS/FPM authority.

### Approved-plan browser controls

The existing Installer shell now provides an access-token form, a single approved-plan
submission action and a read-only status refresh. HTML navigation to `/install/` retains
HTTP 401 until authenticated but displays the login form; API callers retain JSON errors.
Authenticated GET with `Accept: application/json` returns only the current step/status.
The native FPM boundary forwards Accept explicitly. The inline client is authorized by an
exact SHA256 CSP hash, with same-origin connections; no arbitrary inline script allowance.
Token input is cleared after submission, CSRF remains only in memory, and no secret is
written to browser storage. Reload requires authentication again to obtain submission
CSRF. Submission is never automatically retried after a timeout or connectivity error.

Queued/checking does not assert the root worker is running or successful. Status refresh
shows a closed/unavailable message after HTTP 404, not an unverified success claim. There
is no automatic root invocation or bootstrap/product-vhost transition in this change.
Unprepared sessions explicitly report that interactive configuration is unavailable.
Full environment/data/site/Admin form collection and phase-level progress remain open.

Native-web CI runs Chromium desktop/mobile against the real isolated Nginx/FPM TLS surface
using the existing pinned playwright-core dependency. It checks keyboard access, viewport
overflow, invalid/valid login, request publication, single submission, read-only refresh,
offline recovery, empty browser storage and final-lock closure, and exports login/queued
screenshots. The browser ignores only the isolated fixture's self-signed certificate;
separate Python HTTPS assertions verify its certificate. Browser approval/state are fixture
inputs; this is not a second claim of privileged execution or full P21-T016 completion.


### Root preparation timer (development acceptance)

After root has created the private configuration binding and initialized the dedicated
installer state, `install-web-preparation-schedule.php BINDING STATE` validates the
root-owned binding (0600, one link, at most 4096 bytes), canonical state directory,
package identity and literal systemd argument paths. It publishes and enables
`gojet-installer-preparation.service` and `.timer` through the same exclusive,
durable scheduler provisioning guards used by preflight/apply. Existing unit files,
loaded overrides, symlinks and provisioning receipts are conflicts, never replacements.
`render-web-preparation-schedule.php BINDING STATE` performs validation and returns the
unit text without installing it. Both commands require root.

The ten-second timer skips until a configuration draft exists. It invokes only the
packaged preparation worker against the root-selected paths. Any worker started/ready
receipt or final completion node prevents further service execution. The worker also
checks its own receipts, so direct invocation cannot bypass an interrupted preparation.
A service timeout stops the entire process group and leaves the durable barrier intact.
The unit discards stdout, retains only the worker's generic refusal in the journal,
and applies the existing observation service's hardening. Preparation publishes no
approval, database bootstrap or install request. Root review/approval and the separate
browser execution action remain required.

The native payload regression installs the real timer before browser submission,
checks refusal of unprivileged provisioning, unsafe binding permissions/arguments,
existing files, dangling links and interrupted scheduler receipts, then submits the
configuration through TLS/Nginx/FPM. Only the timer creates this scenario's plan.
The fixture verifies root receipt/unit permissions, successful service exit, no second
preparation, no automatic approval/apply request, and the original immutable repeat
check before continuing the existing approval/apply/recovery chain. CI must pass for
this change before these checks count as evidence. Binding/bootstrap provisioning,
explicit preparation recovery and exact Ubuntu 24.04.4 acceptance remain open.


### Recover a published preparation with a missing success receipt

`recover-web-preparation.php BINDING STATE EXPECTED_SEAL_SHA256` is a separate root
operation for one boundary: the complete sealed plan exists, but its worker did not
finish publishing the ready receipt. Stop the preparation timer/service and inspect
the private attempt, binding and plan before choosing the expected seal digest.
Pass the reviewed SHA256 as an explicit argument; the command does not select a plan
or reset an attempt automatically.

Normal workers and recovery now hold the same root0600, single-link, empty
`BINDING.worker.lock` for the entire operation. Busy, linked, writable or malformed
locks refuse the operation. Recovery requires the original started identity, exact
package/source/release, intact plan and TLS files, current dependencies, and frozen
web-draft provenance. It rejects any approval/apply marker, phase journal or final
completion node. A changed draft, missing plan, wrong digest or invalid existing
ready receipt remains blocked. Valid recovery writes only the missing root0600
ready receipt; it preserves the started barrier, plan, web state and generated keys.
A matching repeat verifies and acknowledges the existing receipt without rewriting.
It neither approves nor executes installation.

The native regression constructs the precise published-plan/missing-receipt boundary
in a disposable second plan using the real preparation API. This is an explicit
boundary fixture, not a claim of SIGKILL timing coverage. It checks nonroot rejection,
shared-lock contention, unsafe lock permissions/hardlinks, digest/plan/draft changes,
phase/approval/completion barriers, conflicting receipts, successful recovery and
byte-preserving repeats. The original browser/timer plan then continues through the
existing real approval/apply/recovery flow. No genuine attempt receipt is removed.

This command does not recover an absent/partial plan, permit editing a frozen invalid
configuration, or reset scheduler publication. Those recovery paths remain separate
unfinished work; do not delete receipts or regenerate service keys to bypass them.


### Replace an invalid frozen configuration before any plan is published

The root command `restart-web-configuration.php BINDING STATE NEW_DIRECTORY
EXPECTED_DRAFT_SHA256 BOOTSTRAP_SHA256` retires an unpublished attempt and initializes
a separate attempt. Root must review the old frozen draft digest and select an absent
new directory beneath a root-controlled parent. The bootstrap digest is for the token
that will be used with the new installer FPM configuration; the token itself is never
passed on the command line or copied into state.

Restart shares the preparation worker lock, verifies the package and exact old draft,
and refuses a published plan, ready receipt, approval/apply artifact, final completion,
unsafe/conflicting path or mismatched started record. It first writes an exclusive,
durable root-private `BINDING.retired.json`. The old worker, recovery command and timer
renderer thereafter refuse this attempt; the service condition also skips retired
attempts. The old binding, draft, state and started receipt are never replaced or
removed. An interrupted restart remains retired and requires inspection, not automatic
retry. Restart is not a way to discard or regenerate an already published plan's keys.

The new directory contains root0600 `binding.json` with a new `prepared` destination,
and a fresh installer0700 `state` directory. Root initializes it while its enclosing
directory is still root0700, transfers only those newly created state files to the
installer account, writes the replacement receipt, and finally makes the enclosing
directory traversable (root0755). No existing FPM-owned file is written by root.
Old session/CSRF values, approvals, configuration and generated keys are not copied.
The result prints the new binding/state/prepared paths, never credentials.

This is currently an operator recovery entry point. The active installer FPM state
and bootstrap digest must be switched to the returned state/new token. The existing
`render-web-preparation-schedule.php NEW_BINDING NEW_STATE OLD_BINDING` and
`install-web-preparation-schedule.php NEW_BINDING NEW_STATE OLD_BINDING` commands now
accept an optional predecessor binding. They verify its root retirement/replacement
receipts and the exact successor binding, then use a deterministic per-binding timer
name and separate provisioning receipts. Existing units and receipts are preserved;
the retired attempt cannot run. The original two-argument scheduling entry is unchanged.
The new timer can be installed before configuration submission and waits for its draft.
Automatic persistent FPM configuration switching and restart-publication recovery
remain unfinished; the old page must not be described as reset. Root approval and
browser apply remain separate after new preparation.

Native regression submits a shape-valid but semantically invalid administrator
email as the unprivileged installer and runs the real preparation worker to failure
before plan publication. It covers nonroot/digest/lock/path/approval/plan conflicts,
a simulated interrupted retirement, old-worker/renderer/recovery refusal, preserved
old bytes and fresh ownership/session state. Corrected submission uses the existing
real browser/TLS/FPM helper against the replacement state, including HTTP rejection
of the old session. Its isolated successor timer alone prepares the new plan; old
scheduler receipts remain unchanged. The shared scheduler publication failure matrix
runs once in the original scenario; the replacement adds only lineage-specific checks.
Browser evidence is stored separately under `payload/browser-replacement`. This proves
new-state browser submission and scheduling, not automated switching of a persistent
production FPM pool, and it creates no approval or data execution.
